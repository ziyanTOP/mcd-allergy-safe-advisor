# 麦麦安心点单官 · McD Allergy-Safe Advisor

> 基于**麦当劳 MCP** 的过敏原与忌口安全点单顾问。
> 让"我有花生过敏，还能吃麦当劳吗"这个问题，在 30 秒内得到可执行答案。

**目标用户**：有食物过敏、乳糖不耐受、麸质禁忌、减脂控钠需求，却仍然想吃麦当劳的 1.2 亿中国消费者；
以及替孩子/家人点单、不想靠猜的父母。

---

## 为什么做这个

麦当劳 MCP 已经提供了菜单、营养、门店、价格、优惠券、积分、主题活动共 **35 个工具**，
但它**没有暴露过敏原字段**——实测 `list-nutrition-foods` 只返回能量、蛋白质、脂肪、碳水、钠、钙
（返回体是形如 `[160]{productName,energyKcal,protein,...}:` 的 CSV 字符串）。

于是产生了一个真实而高频的空白：

> 用户知道自己不能吃什么，但不知道**这家店今天在卖的哪些东西**碰了那些东西。

现有做法要么是让用户自己在 App 里一项项猜，要么是查一份过期几个月的静态配料表。
**本项目用 MCP 把"这家店现在真实可售的菜单"拉出来，再叠加一层可审计的过敏原语义与交叉接触分析，
输出的是"能不能吃 + 怎么改 + 到店怎么说"三件套。**

## 双层知识设计：为什么有两个 data 文件

| 文件 | 角色 | 来源 | 证据等级 |
|---|---|---|---|
| `data/mcp_observed_vocabulary.json` | **实测层** | `scripts/build_ground_truth.py` 直接抓取 MCP 真实响应生成 | 客观抓取，但由关键词分析反推，**属观察提示** |
| `data/allergen_matrix.json` | **知识层** | 依据公开产品信息人工整理的中国区过敏原矩阵 | 人工知识，每条带 `confidence` 与 `source` |

引擎在处理时严格区分这两者：

- 知识层的过敏原命中 → **硬命中**，直接影响等级（⛔ / 🟡）；
- 实测层的观测提示 → 只降为 **🟠 需确认**，并注明"需到店核实"，**不会直接判为不可选**；
- 两层与实时 MCP 数据（名称、标签、必含成分、可去除配料）三者共同参与判定，实时数据优先级最高。

这样做的原因很实际：实测底库由关键词分析反推，天然会有边界误差（例如植物奶含"奶"字）。
把它放在"提示"而不是"结论"层，既用上了 MCP 实测的广度，又不会因为误判把安全餐品一票否决。

## 关键技术发现（实测得出，不是猜的）

开发过程中通过抓取真实 MCP 响应，摸清了三个决定成败的结构性事实：

**1. `query-meals` 不返回餐品名。** 它的 `data.categories[].meals[]` 每项只有 `code` 与 `tags`，
价格在另一张 `data.meals` 映射表里，**餐品名、套餐组成、可去除配料全都藏在 `query-meal-detail`**。
所以真实链路必须是"菜单 → 逐个详情"的两跳调用（本项目用本地缓存把 68 个餐品的详情拉完只需 ~12 秒）。

**2. `modification` 里的配料分三档，语义完全不同：**

| MCP 字段 | 含义 | 判定处理 |
|---|---|---|
| `rounds` / `choices` | 餐品**必含**成分 | 命中过敏原 → ⛔ 不建议 |
| `modification.values` 且 `minQuantity ≥ 1` | **必选**配料，无法去除 | 命中过敏原 → ⛔ 不建议 |
| `modification.values` 且 `minQuantity == 0` 且 `selectedQuantity ≥ 1` | **默认已加但可去掉** | 命中过敏原 → 🟡 给出"不加 X" |
| `modification.values` 且 `selectedQuantity == 0` | 默认不加的**可选加料** | 仅提示，不算命中 |

这个区分直接决定了准确率：不做区分时，"小杯鲜萃咖啡"会因为默认加了奶油球被误判成含乳制品，
而"冰燕麦奶铁"会因为含"奶"字被误伤。

**3. 菜单里会藏"选品器"。** `鸡肉堡单品精选`、`学生专享饮品随心选` 这类不是具体餐品，
本项目通过名称特征识别并单独归类，避免给出无意义的"推荐"。

## 核心能力

| 能力 | 说明 |
|---|---|
| 🧾 **实时菜单安全筛查** | 拉取门店在售菜单，逐项判定过敏原命中，分出 ✅安心 / 🟡可去除后可选 / 🟠谨慎 / ⛔不建议 |
| 🔧 **可执行的去险方案** | 不是只说"含芝士"，而是给出"去芝士 + 去千岛酱 + 换无芝麻面包"的具体动作 |
| 🧪 **交叉接触推理** | 建模共用炸锅 / 烤面包机 / 烤架，识别"配料表没写但仍可能中招"的场景 |
| 🗣️ **到店话术生成** | 生成一段可直接念给店员的话，把"我不吃 X"变成店员能执行的动作 |
| 📊 **营养与预算约束** | 在同等安全的候选中按热量、钠、蛋白排序，并用 `calculate-price` 校验预算 |
| 🇨🇳 **中国区专属知识** | 中国区薯条配方不含小麦与乳（与美国区不同）、酱料含蛋含大豆等本地事实 |

## 麦当劳上新了，这个技能怎么处理？

这是本项目最被低估的设计点。答案不是"上新就完蛋"，而是**四层防线 + 自动补录闭环**。

### 防线一：新品天然进入实时链路

新品不需要任何配置。`query-meals` 返回的是**这家店此刻的编码表**，
新品的编码会自动出现在里面 → 自动拉 detail → 自动参与分级。
从麦当劳上新到技能能识别，中间**不需要人做任何事**。

### 防线二：顺着 code 把"套餐引用的隐藏子餐品"也拉进来

实测发现：麦当劳 MCP 的套餐子项经常引用**没有在分类里单列**的餐品
（如 `大杯玉米杯`、`麦咖啡™冰美式中杯`），只在 `rounds[].choices[].code` 里留了个编码。

本项目会收集这些编码，**再拉一轮 `query-meal-detail`** 把它们补进同一张菜单：

```
68 个分类内餐品  →  107 个（含 39 个套餐隐藏子项）
```

这一步让"套餐的过敏原"能真正继承子餐品的判定（套餐里有芝士厚牛堡 → 套餐也含乳）。

### 防线三：成分解析四级兜底

| 顺序 | 来源 | 示例 |
|---|---|---|
| 1 | 知识库餐品/酱料表 | `甜酸酱` → 含大豆 |
| 2 | 同门店菜单内的其他餐品 | `小杯玉米杯` → 用它自己的判定结果 |
| 3 | 制作选项与已知安全成分 | `去冰`（不是成分）、`切块生菜`（无主要过敏原） |
| 4 | 过敏原关键词兜底 | `浓郁奶香拉丝芝士` → 含乳 |

### 防线四：未知即降级，绝不假装安全

**这是最关键的一条**：如果某个成分在以上四级都判不出来，
该餐品**不会被判为"安心"**，而是降级为 🟠「需到店确认」，并在报告里给出：

```
## 📌 知识库待补充（新品自动入队）

以下成分在知识库中没有收录，无法确认过敏原，相关餐品已自动降级为「需确认」：

- `烤味酱`（被 1 个餐品引用）
- `烤牛肉风味酱`（被 1 个餐品引用）
```

### 闭环：待补充队列 → 人工补录 → 下次就准

```
新品上架
   ↓
自动进入「待补充」队列（报告里可见）
   ↓
人工在 data/allergen_matrix.json 的 items / sauces 补一条（带 confidence）
   ↓
下次运行 → 该成分被解析 → 相关餐品从 🟠 变 ✅ / ⛔，队列清空
```

本项目自己的两个新酱料 `烤味酱`、`烤牛肉风味酱`（2026 龙焰系列新品）
就是这样从队列里收进来��—`confidence: "low"`，并标注"需到店核实"。

配套工具：`scripts/build_ground_truth.py` 可随时重抓 MCP 底库，
刷新 `data/mcp_observed_vocabulary.json`，让知识层始终跟得上菜单。

### 一句话总结

> 菜单变了，**分级逻辑不用改**；变的是"知识库缺了几条"，
> 而缺失会被自动暴露成一份待办清单，而不是变成一个静默的错误推荐。

## 菜单真实性校验：只推荐这家店此刻真在卖的

"很多餐品当季就不卖了"——这不是假设，是实测。

拿同一家门店跑一遍，**静态知识库 30 条餐品里只有 8 条在该店当前在售**，
另外 **22 条本店根本没上架**，其中包括巨无霸、薯条、麦香鱼、麦满分这些主力单品。
如果按静态知识库推荐，用户拿着清单去店里会发现一半买不到。

所以本项目有四条硬约束：

### 1. 分级对象只来自 MCP 实时返回

所有被分级、被推荐的餐品，**无一例外来自 `query-meals` 的返回体**。
静态知识库只提供"这个名字含什么过敏原"的语义，**绝不提供"有什么可以点"**。
测试里有断言守着这条线：静态库里的条目不会因为知识库里有就出现在建议中。

### 2. 报告顶部标明来源与采样时间

```
> 📍 **菜单来源**：麦当劳 MCP 实时返回（query-meals + query-meal-detail）
> ｜ 门店 1450197 ｜ 采样时间 2026-10-23T21:57:35+08:00 ｜ 覆盖 107 个在售餐品
>
> 本方案只覆盖该门店此刻在售的餐品；静态知识库仅提供过敏原语义，不提供可点菜品。
```

不同门店、不同时间跑出来的方案**不会一样**，因为菜单本身就在变。

### 3. 时效性单独提示

带「限时特惠 / 上新 / 限定 / 麦金卡」标签的餐品会被单独标出——它们会随活动结束下架：

```
⏳ 时效性提示：14 个餐品带「限时/上新/限定/麦金卡」标签，可能随活动结束下架，建议尽早下单：
- 心形薯饼8块（限时特惠、上新）
- 龙焰鸡腿堡（韩式辣椒黄油风味、上新）
- 培根安格斯厚牛堡四件套（麦金卡）
```

### 4. 非食品 / 周边不参与分级

玩具、赠品（如"海绵宝宝×航海王系列玩具"、"按摩捶痒痒挠"）会被识别出来，
单独归组，不混进"安心推荐"——它们没有过敏原，但推荐它们也没意义。

### 5. 知识库在售对照

报告里始终给一张对照表，让人知道知识库与现实差多少：

```
📚 知识库在售对照：知识库共 30 条餐品，其中 8 条在本店当前在售，
   22 条本店未上架（已自动排除，不参与推荐）。
```

> 换句话说：**知识库会过期，但分级逻辑不会。**
> 过期的是"这个店卖什么"，而那部分每次都从 MCP 现拉；知识库只负责"这个东西含什么"，
> 并且它的过期程度会通过这张对照表被诚实地暴露出来。

## 风险分级模型

引擎把过敏原信号分成**三层**，实时 MCP 数据的优先级最高：

```
第一层：名称 + 标签 + 必含成分(rounds/choices/必选modification) + 静态知识库
   └─ 命中过敏原            → ⛔ 不建议（或静态库给出的"去芝士/去酱"方案 → 🟡）
第二层：默认已加但可去除的 modification（minQuantity=0 且 selectedQuantity≥1）
   └─ 命中过敏原            → 🟡 去除配料后可选，动作直接取自 MCP（如"不加辣椒黄油风味酱"）
第三层：默认不���的可选加料 + may_contain + 交叉接触
   └─ 命中过敏原            → 🟠 谨慎，建议到店确认
严格模式下，交叉接触同样判为 ⛔。
```

组合级检查：订单中若既有可食用项又有风险项，会提示**分单取餐**，因为取餐台与设备是共用的。

两个容易出错、已专门处理的细节：

- **植物奶不算乳制品**：`燕麦奶`、`植物奶` 等含"奶"字但无乳，关键词解析会专门排除；
- **忌口词按菜单写法扩展**：`牛肉` 会同时命中"厚牛堡""安格斯""牛柳"，但**不会**误伤"纯牛奶"。

## 设计原则

1. **实时事实必须来自 MCP**——门店可售菜单、价格、优惠每天在变，静态表回答不了"今天有没有"。
2. **过敏判定取并集**——实时标签与静态知识库冲突时按更保守的一侧走，宁可多提醒。
3. **不夸大确定性**——每条结论都带风险等级与来源标注，并附到店确认话术。
4. **不替代医疗建议**——严重过敏者请以门店现场为准，并自行携带急救药物。
